# 02 进程管理

> 本章是操作系统**分值最高、最核心**的章节，涵盖进程与线程基础、进程同步与互斥、处理机调度及死锁四大板块。PV 操作大题和调度算法计算是历年必考重点。

## 一、进程与线程

### 1.1 进程的概念

引入进程的目的是**更好地描述和控制程序的并发执行**。

- **进程实体（进程映像）**= 程序段 + 数据段 + PCB（进程控制块）
- 进程实体是**静态**的，进程是**动态**的运行过程
- **PCB 是进程存在的唯一标志**

> 进程定义："进程是进程实体的运行过程，是系统进行**资源分配和调度**的一个独立单位。"

### 1.2 进程的特征

1. **动态性**（最基本特征）：具有生命周期，动态产生、变化和消亡
2. **并发性**（重要特征）：多个进程实体可在一段时间内同时运行
3. **独立性**：进程是独立运行、获得资源、接受调度的基本单位
4. **异步性**：进程按各自独立的、不可预知的速度向前推进
5. **结构性**：每个进程都配置一个 PCB

### 1.3 进程的状态与转换

进程有 **5 种状态**，其中前 3 种为基本状态：

```
          时间片用完/被抢占
     ┌──────────────────────┐
     │                      ▼
 就绪态 ──调度──▶ 运行态 ──等待事件──▶ 阻塞态
     ▲                                  │
     └────────── 事件发生 ◀──────────────┘
```

- **就绪态 → 运行态**：被调度，获得处理机
- **运行态 → 就绪态**：时间片用完 / 被更高优先级进程抢占
- **运行态 → 阻塞态**：请求资源或等待事件（**主动行为**）
- **阻塞态 → 就绪态**：等待的事件发生（**被动行为**，需其他进程协助）
- **创建态 → 就绪态**：PCB 初始化完成、资源分配就绪
- **运行态 → 终止态**：正常结束或异常中断

> [!WARNING] 易错点
> 不存在 **阻塞态 → 运行态** 的直接转换！阻塞态必须先变为就绪态，再被调度变为运行态。

### 1.4 进程控制

进程控制使用**原语**实现（原子操作，不可中断）：

| 原语 | 功能 |
|------|------|
| 创建原语 | 分配 PID → 申请 PCB → 分配资源 → 初始化 PCB → 插入就绪队列 |
| 撤销原语 | 检索 PCB → 终止执行 → 终止子孙进程 → 归还资源 → 删除 PCB |
| 阻塞原语 (Block) | 找到 PCB → 保护现场 → 状态置为阻塞 → 插入等待队列 |
| 唤醒原语 (Wakeup) | 找到 PCB → 移出等待队列 → 状态置为就绪 → 插入就绪队列 |

> [!IMPORTANT] Block 和 Wakeup 必须成对使用。

### 1.5 进程通信

| 方式 | 原理 | 特点 |
|------|------|------|
| **共享存储** | 进程间共享一块内存空间 | 需互斥访问（PV 操作），需系统调用实现 |
| **消息传递** | 以格式化的消息为单位交换数据 | 直接通信（消息缓冲队列）/ 间接通信（信箱） |
| **管道通信** | 通过共享文件（pipe）以字符流传输 | 半双工、固定大小缓冲区、自带同步互斥机制 |

管道通信要点：
- 管道是固定大小缓冲区（Linux 中 4KB）
- **写满后写阻塞**，**读空后读阻塞**
- 读数据是**一次性操作**
- **半双工**通信，全双工需要**两个管道**

### 1.6 线程

引入线程是为了**减小并发执行时的时空开销**。

| 对比项 | 进程 | 线程 |
|--------|------|------|
| 调度 | 资源分配的基本单位 | **处理机调度的基本单位** |
| 资源 | 拥有系统资源 | 基本不拥有资源，共享进程资源 |
| 并发性 | 进程间可并发 | **线程间也可并发** |
| 系统开销 | 创建/切换**开销大** | 创建/切换**开销小** |
| 通信 | 需同步互斥机制 | 可直接读写进程数据段 |

线程的实现方式：

| 方式 | 特点 |
|------|------|
| 用户级线程 (ULT) | 线程管理在用户空间，内核不感知，只能用一个 CPU |
| 内核级线程 (KLT) | 内核管理，可使用多 CPU，切换效率较低 |
| 组合方式 | 多个 ULT 映射到少量 KLT |

多线程模型：
- **多对一**：多个 ULT → 一个 KLT（一个阻塞全部阻塞）
- **一对一**：每个 ULT → 一个 KLT（并发能力强，开销大）
- **多对多**：n 个 ULT → m 个 KLT（折中方案，m ≤ n）

## 二、处理机调度

### 2.1 调度的层次

| 层次 | 别名 | 功能 | 频率 |
|------|------|------|------|
| **作业调度** | 高级调度 | 从外存选择作业调入内存，创建进程 | 低（分钟级） |
| **内存调度** | 中级调度 | 将暂时不能运行的进程挂起到外存 | 中 |
| **进程调度** | 低级调度 | 从就绪队列选进程分配处理机 | **最高**（毫秒级） |

> [!IMPORTANT] 进程调度是最基本的，不可或缺。

### 2.2 调度方式

- **非剥夺（非抢占）**：进程一旦获得 CPU 就保持到终止或阻塞
- **剥夺（抢占）**：可被更高优先级进程抢占，适用于分时/实时系统

### 2.3 调度的评价指标

- **CPU 利用率** = CPU 忙碌时间 / 总时间
- **系统吞吐量** = 单位时间完成的作业数
- **周转时间** = 完成时间 − 提交时间
- **带权周转时间** = 周转时间 / 实际运行时间
- **等待时间** = 进程处于等待处理机状态的时间之和
- **响应时间** = 从提交请求到首次产生响应的时间

### 2.4 典型调度算法

#### FCFS（先来先服务）

- **不可剥夺**，按到达顺序调度
- 对长作业有利，对短作业不利
- 有利于 CPU 繁忙型，不利于 I/O 繁忙型
- 不能作为分时/实时系统的主要调度策略

#### SJF（短作业优先）

- **不可剥夺**（SRTN 为可剥夺版本），选择估计运行时间最短的
- **平均等待时间、平均周转时间最少**
- 对长作业不利，可能产生**饥饿**
- 未考虑作业紧迫程度

#### 优先级调度

- 选择优先级最高的进程
- 非剥夺式 / 剥夺式
- 静态优先级 / 动态优先级
- 一般原则：系统进程 > 用户进程，交互型 > 非交互型，I/O 型 > 计算型

#### HRRN（高响应比优先）

$$R_p = \frac{\text{等待时间} + \text{要求服务时间}}{\text{要求服务时间}}$$

- 等待时间相同 → 短作业优先
- 服务时间相同 → 先来先服务
- 长作业等待足够久也能获得处理机 → **克服饥饿**

#### RR（时间片轮转）

- 就绪进程按 FCFS 排列，每个进程执行**一个时间片**后轮转
- 主要适用于**分时系统**
- 时间片太大 → 退化为 FCFS；时间片太小 → 频繁切换开销大

#### 多级反馈队列

- 设置**多个就绪队列**，优先级递减，时间片递增
- 新进程先入第 1 级队列，若时间片内未完成则降入下一级
- 仅当高优先级队列为空时才调度低优先级队列
- **时间片轮转 + 优先级调度的综合**

> [!IMPORTANT] 多级反馈队列调度算法
> 这是考研中最常考的调度算法，它兼顾了短作业、I/O 型进程和长作业。新进入的高优先级进程**会抢占正在运行的低优先级进程**。

**执行过程示例**：

```
第1级队列（优先级最高，时间片=1）：A → B → C
第2级队列（优先级次高，时间片=2）：
第3级队列（优先级最低，时间片=4）：FCFS
```

1. A 进入第 1 级队列 → 获得 1 个时间片 → 未完成 → 降入第 2 级
2. B 进入第 1 级队列 → 获得 1 个时间片 → 未完成 → 降入第 2 级
3. 第 1 级队列空 → 调度第 2 级队列中的 A → 获得 2 个时间片
4. 若此时新进程 D 到达第 1 级 → **抢占** A → A 回到第 2 级队列队尾

## 三、进程同步

### 3.1 基本概念

- **临界资源**：一次仅允许一个进程使用的资源
- **临界区**：访问临界资源的那段代码
- **同步（直接制约）**：多个进程需要在某些位置上**协调工作次序**
- **互斥（间接制约）**：一个进程使用临界资源时，其他进程必须等待

同步机制应遵循的准则：
1. **空闲让进**：临界区空闲时允许进入
2. **忙则等待**：有进程在临界区时其他进程等待
3. **有限等待**：保证能在有限时间内进入临界区
4. **让权等待**：不能进入时应释放处理器

### 3.2 信号量机制

信号量是一种功能强大的同步工具，由 Dijkstra 提出。

**整型信号量**：

```c
wait(S) {          // P 操作
    while (S <= 0); // 忙等
    S--;
}
signal(S) {        // V 操作
    S++;
}
```

**记录型信号量**（推荐使用）：

```c
typedef struct {
    int value;       // 资源数量
    struct process *L; // 等待队列
} semaphore;

void wait(semaphore S) {   // P 操作
    S.value--;
    if (S.value < 0)        // 无资源可用
        block(S.L);         // 阻塞自己，挂到等待队列
}
void signal(semaphore S) {  // V 操作
    S.value++;
    if (S.value <= 0)       // 有进程在等待
        wakeup(S.L);        // 唤醒等待队列中的一个进程
}
```

> [!IMPORTANT] PV 操作核心要点
> - P 操作（wait）：申请资源，`value--`，若 `value < 0` 则阻塞
> - V 操作（signal）：释放资源，`value++`，若 `value ≤ 0` 则唤醒一个等待进程
> - `|value|`（当 value < 0 时）= 等待队列中的进程数

### 3.3 经典同步问题

#### 生产者-消费者问题

```c
semaphore mutex = 1;   // 互斥访问缓冲区
semaphore empty = n;   // 空缓冲区数量
semaphore full = 0;    // 满缓冲区数量

// 生产者                    // 消费者
producer() {                consumer() {
    while(1) {                  while(1) {
        produce();                  P(full);    // 有产品？
        P(empty);   // 有空位？     P(mutex);   // 互斥进入
        P(mutex);   // 互斥进入     take();
        put();                      V(mutex);
        V(mutex);                   V(empty);   // 空位+1
        V(full);    // 产品+1       consume();
    }                           }
}                           }
```

> [!WARNING] PV 操作顺序
> **实现互斥的 P 操作一定要在实现同步的 P 操作之后**，否则可能死锁！V 操作顺序无要求。

#### 读者-写者问题

```c
semaphore rw = 1;      // 读写互斥
semaphore mutex = 1;   // 保护 count
int count = 0;         // 读者计数

// 写者                      // 读者
writer() {                  reader() {
    while(1) {                  while(1) {
        P(rw);                      P(mutex);
        write();                    if (count == 0) P(rw);
        V(rw);                      count++;
    }                               V(mutex);
}                                   read();
                                    P(mutex);
                                    count--;
                                    if (count == 0) V(rw);
                                    V(mutex);
                                }
                            }
```

#### 哲学家进餐问题

5 个哲学家围坐，每人左右各一根筷子，需两根才能吃饭。

防止死锁的方案：
1. 最多允许 4 个哲学家同时拿筷子
2. 奇数号先拿左筷子，偶数号先拿右筷子
3. 仅当左右两根筷子都可用时才一起拿起（用 AND 信号量）

#### 吸烟者问题

三种材料（烟草、纸、胶水），三个吸烟者各有一种，供应者每次提供两种。本质是**单生产者-多消费者**问题。

#### 理发师问题（服务-被服务型）

> [!IMPORTANT] 理发师问题 = 生产者-消费者的变式
> 将**顾客**和**服务员**分别视为一种资源。本质是服务与被服务关系，需要额外设置 `waiting` 变量记录等待人数。

**基本模型**：理发店有 1 位理发师、n 把椅子。无顾客时理发师睡眠，顾客到来唤醒理发师。

```c
semaphore customer = 0;   // 等待的顾客数（同步信号量）
semaphore barber = 0;     // 理发师是否空闲（同步信号量）
semaphore mutex = 1;      // 互斥访问 waiting
int waiting = 0;          // 等待的顾客数（普通变量）

barber() {
    while(1) {
        P(customer);      // 无顾客则睡眠
        P(mutex);
        waiting--;
        V(barber);        // 理发师准备好了
        V(mutex);
        理发;
    }
}

customer_i() {
    P(mutex);
    if(waiting < n) {     // 有空椅子
        waiting++;
        V(customer);      // 唤醒理发师
        V(mutex);
        P(barber);        // 等待理发师空闲
        接受理发;
    } else {
        V(mutex);         // 没有空椅子，离开
    }
}
```

### 3.4 PV 操作大题解题方法论

> [!IMPORTANT] 大题六步法（2009-2022 年，PV 大题考频 10 次）
> PV 操作大题是操作系统**最高频的大题类型**，需要系统化的解题框架。

**第 1 步：确定进程数**
- 梳理题目中有几类进程（动作不同 = 不同类进程）
- 一个进程对应一个函数

**第 2 步：确定动作**
- 每个进程的动作是什么（允许伪代码形式答题）
- 动作执行一次（不加 while）还是重复（`while(1)` 循环）

**第 3 步：确定 P 操作**
- 消耗资源型 P：题目显式给出的资源消耗
- 互斥型 P：隐含的互斥关系（如缓冲区互斥访问）
- **同步 P 一定要在互斥 P 之前**（先拿空间再上锁）

**第 4 步：确定 V 操作**
- 每个 P 必有对应的 V
- 思考 V 应放在哪个进程的哪个位置

**第 5 步：确定信号量初值**
- 互斥信号量 = 1
- 同步信号量 = 初始资源数

**第 6 步：检查死锁**
- 连续多个 P 操作处是否可能死锁
- P 同步信号量在前、P 互斥信号量（mutex）在后 → 不死锁

### 3.5 管程

管程是一种高级同步机制，将共享变量及其操作**封装在一个模块**内：

- 每次仅允许**一个进程进入管程**
- 进程通过调用管程中的过程来间接访问共享数据
- 使用**条件变量**配合 `wait()` 和 `signal()` 实现同步

## 四、死锁

### 4.1 死锁的概念

死锁是指多个进程因**竞争资源而造成的一种互相等待**的僵局。

### 4.2 死锁产生的四个必要条件

1. **互斥条件**：资源一次只能被一个进程使用
2. **不剥夺条件**：进程已获得的资源在未使用完之前不能被强行夺走
3. **请求并保持**：进程持有资源的同时又请求新资源
4. **循环等待**：存在进程资源的循环等待链

> [!IMPORTANT] 死锁判定：资源分配图简化
> **死锁定理**：S 为死锁状态的充要条件是 S 的资源分配图是不可完全简化的。
> 
> **简化步骤**：
> 1. 找一个**不阻塞**的进程（即其请求的资源数 < 系统剩余空闲资源数）。
> 2. 消去该进程的所有请求边和分配边（将其资源视为归还系统）。
> 3. 重复上述步骤，直到无法继续。
> 4. 若所有边都能消去 → **无死锁**；若仍有边残留 → **有死锁**（残留边关联的进程即为死锁进程）。

> [!IMPORTANT] 四个条件缺一不可
> 只要破坏其中任一条件，就能预防死锁。

### 4.3 死锁的处理策略

#### 死锁预防（静态策略）

| 破坏条件 | 方法 | 缺点 |
|---------|------|------|
| 互斥 | 将独占资源改为共享（如 SPOOLing） | 大多数资源无法改造 |
| 不剥夺 | 进程请求新资源失败时释放已有资源 | 反复申请释放，开销大 |
| 请求并保持 | 进程运行前一次性申请所有资源 | 资源利用率低，可能饥饿 |
| 循环等待 | 对资源编号，按序申请 | 编号不便，限制新设备 |

#### 死锁避免（动态策略）— 银行家算法

在资源分配前判断是否会导致系统进入**不安全状态**。

**安全状态**：存在一个**安全序列**，使得所有进程都能顺利完成。

银行家算法的数据结构：
- `Available[j]`：系统中第 j 类资源的可用数量
- `Max[i][j]`：进程 i 对第 j 类资源的最大需求
- `Allocation[i][j]`：进程 i 已分配的第 j 类资源数
- `Need[i][j]` = `Max[i][j]` − `Allocation[i][j]`：进程 i 还需要的资源数

安全性检查算法：
1. 初始化 `Work = Available`
2. 找一个满足 `Need[i] ≤ Work` 的进程 i
3. 若找到：`Work = Work + Allocation[i]`，标记进程 i 完成，回到步骤 2
4. 若所有进程都标记完成 → **安全状态**；否则 → **不安全状态**

> [!IMPORTANT] 银行家算法计算题
> 这是操作系统**必考计算题**之一。注意：不安全状态**不一定**会死锁，但死锁一定处于不安全状态。

#### 死锁检测与解除

- **资源分配图**：检测是否存在死锁
  - 简化方法：找到一个不阻塞的进程，消去其所有请求边和分配边，若最终能消去所有边则无死锁
- **死锁解除**：
  - 资源剥夺法：挂起死锁进程，剥夺其资源
  - 撤销进程法：撤销代价最小的死锁进程
  - 进程回退法：让进程回退到足以避免死锁的地步
